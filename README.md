# House Price Prediction API with Automated CI/CD

A machine-learning-powered REST API for house price prediction, containerized with Docker and deployed through an automated CI/CD pipeline using Jenkins and Kubernetes.

---

## 📌 Project Overview

This project combines a **Machine Learning prediction API** with a complete **CI/CD and container orchestration workflow**.

The application is built using **FastAPI** and a **Random Forest Regression** model. Users provide basic house details such as area, number of bedrooms, bathrooms, and parking spaces. The API returns a predicted house price in lakhs.

The application is then:

1. Stored in GitHub
2. Tested automatically using pytest
3. Containerized using Docker
4. Published to Docker Hub
5. Deployed to Kubernetes using Minikube
6. Updated automatically through Jenkins when changes are detected

---

## 🎯 Objectives

- Build a REST API for house price prediction.

## 🤖 Machine Learning Component

The project uses a **Random Forest Regressor** from scikit-learn.

The model receives four input features:

| Feature | Description |
|---|---|
| `area_sqft` | House area in square feet |
| `bedrooms` | Number of bedrooms |
| `bathrooms` | Number of bathrooms |
| `parking` | Number of parking spaces |

The trained model is saved as:

```text
model/house_price_model.pkl
```

The model is loaded by the FastAPI application when the application starts.

### Model Training

The training script is:

```text
train_model.py
```

It creates the training data, trains the Random Forest model, and saves the trained model using `joblib`.

# 🐳 Docker

The application is containerized using Docker.

The Docker image:

# ⚙️ Jenkins CI/CD Pipeline

The CI/CD pipeline is defined in:

```text
Jenkinsfile
```

### Pipeline Stages

```text
Checkout
   ↓
Setup Python Environment
   ↓
Install Dependencies
   ↓
Run Tests
   ↓
Build Docker Image
   ↓
Login to Docker Hub
   ↓
Push Docker Images
   ↓
Deploy to Kubernetes
   ↓
Wait for Rollout
```

### Pipeline Behavior

When a change is pushed to GitHub, Jenkins detects the change using **SCM polling**.

The pipeline then:

1. Checks out the latest source code.
2. Creates a Jenkins-specific Python virtual environment.
3. Installs the dependencies.
4. Runs the automated test suite.
5. Builds a Docker image using the Jenkins build number.
6. Logs into Docker Hub using Jenkins credentials.
7. Pushes the versioned image.
8. Pushes the `latest` image.
9. Updates the Kubernetes Deployment.
10. Waits for the Kubernetes rollout to complete.

If the tests fail, the pipeline does not proceed to the Docker build and deployment stages.

# 🔄 Kubernetes Rolling Updates

The Deployment uses the Kubernetes:

```text
RollingUpdate
```

strategy.

When the application image is updated, Kubernetes replaces the old Pods according to the Deployment's rolling-update configuration rather than requiring the entire Deployment to be manually recreated.

Jenkins waits for the rollout to complete using:

```bash
kubectl rollout status deployment/house-price-api
```

---

# 📈 Kubernetes Scaling

The application can be scaled using:

```bash
kubectl scale deployment house-price-api --replicas=4
```

The Deployment can then be returned to two replicas:

```bash
kubectl scale deployment house-price-api --replicas=2
```

The project was tested with scaling from **2 replicas to 4 replicas and back to 2 replicas**.

---

# 🔄 Kubernetes Self-Healing

Kubernetes maintains the desired number of replicas.

If one of the application Pods is deleted:

```bash
kubectl delete pod <pod-name>
```

the Deployment controller detects that the actual number of Pods is below the desired replica count and creates a replacement Pod.

This demonstrates Kubernetes' self-healing behavior.

# 🔐 Security Considerations

Sensitive credentials are not stored in the source code.

The project uses:

- `.gitignore` for local environment and secret files
- Jenkins Credentials for Docker Hub authentication
- Docker Hub access token instead of storing a Docker Hub password in the Jenkinsfile

The Docker Hub credential is referenced in Jenkins using the credential ID:

```text
dockerhub
```

Credentials should never be committed to GitHub.
